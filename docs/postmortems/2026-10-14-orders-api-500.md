# Post-incident review: orders API returned 500 for signed-out users

**Date:** 2026-10-14  ·  **Status:** final  ·  **Author:** Mahmoud Mohamed

## Summary

`GET /api/getUserOrders` crashed with a 500 error instead of answering 401 when nobody was signed in, and also crashed for a signed-in email with no account record. It was found while writing automated tests, fixed the same day, and is now covered by tests in CI and by the smoke test.

## Impact

- Any signed-out request to the route got a 500 instead of a clear "sign in" response.
- A signed-in user whose email had no `User` record (for example, if the record was deleted) also got a 500.
- We can't measure how often this happened in production: at the time the app had no request logs, no health checks and no monitoring. That gap is itself one of the findings below.

## Timeline

| When | What happened |
| --- | --- |
| Before 2026-10-14 | The route reads `session.user.email` and `user.id` without checking either. |
| 2026-10-14 | Writing a Jest test for the signed-out case reproduces the crash: `TypeError: Cannot read properties of null`. |
| 2026-10-14 | Fix: the route returns 401 when there is no session and 404 when the account doesn't exist. Three tests cover 401, 404 and the normal case; GitHub Actions runs them on every push. |
| 2026-10-16 | Follow-ups below: health endpoint, request IDs and structured logs, a smoke test that checks this route returns 401, and an hourly uptime check. |

## Root cause

The route trusted its inputs. `getServerSession` returns `null` for signed-out requests, and `prisma.user.findUnique` returns `null` for an unknown email; the code dereferenced both without checking.

It wasn't caught earlier because the project had no automated tests, and nothing in production would have surfaced it: no logs, no error tracking, no health checks. Other routes had the opposite problem: they caught errors but threw away the details, so failures were invisible.

## What went well / what didn't

- **Went well:** writing a test for the unhappy path found the bug immediately, and the fix was small and easy to verify.
- **Didn't go well:** the bug could only have been found by a user, and there was no way to tell whether it had already happened in production.
